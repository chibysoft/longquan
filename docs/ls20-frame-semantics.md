# ls20 帧语义分析 + move 的 init 设计（认知活）

> 2026-09-05 · Longquan 龙泉 · 推进核认知活输出（含线上探路结论）
> 目的：为 move 原语的 `init(帧 -> WorldState)` 钉死「从帧里提取什么、怎么提取」。
> 方法：读固化帧 + **线上发单步动作实测**（设计期参考，非运行时输入）。**不读源码**（官方引擎源码已移出版本库）。

---

## 0. 一句话结论（本次认知活最重要的发现，共两条）

1. **ls20 不是「3px/cell 的 21×21 均匀网格」，是「像素级的房间导航游戏」。** 之前 fixtures/README.md 里「棋盘格=3×3 像素、棋盘 21×21」是从 AR25 **错误继承**的假设，对 ls20 不成立。起始形状 7×7、移动对象 5×2、目标标记 3×3、地板 40×25——**都不是 3 的倍数**。

2. **「谁在动」单帧看不出，必须线上发动作实测。** 文档初稿凭单帧误判「光标=色0/1、目标槽标记=色12」。线上发 ACTION1 实测后纠正：**移动对象=色12（5×2 块），色0/1（3×3）是静止目标标记**。移动步长=5px，ACTION1/2/3/4=上/下/左/右。

这再次印证方向 B 的认知：**ARC-AGI-3 是交互引擎，每个游戏的帧结构和动态语义都不一样，不能用 AR25 的感知层硬套。** move 的 `init` 必须为 ls20 重新写「帧 → 状态」的提取。

## 3. 颜色语义（更正 AR25，且更正本文件初稿）

perceive.py 的 `COLOR_BG=9 / COLOR_TARGET=11 / COLOR_LINE=10` 是 AR25 特化，对 ls20 **完全错误**。ls20 的色语义：

| 色 | ls20 语义 | 初稿误判 | 实测纠正 |
|----|----------|---------|---------|
| 0 | 目标标记主体 | 光标主体 | **静止目标，不是玩家** |
| 1 | 目标标记轮廓 | 光标轮廓 | 静止目标 |
| 3 | **地板（walkable）** | 地板 | ✅ 移动对象在色3上移动 |
| 4 | 墙/背景（障碍） | 墙 | ✅ 撞上停住 |
| 5 | 起始形状 + 目标槽 + UI | 起始形状 | ✅ 撞上停住 |
| 9 | 目标色标记 | GoalColor | ✅ 撞上停住 |
| 11 | 步数进度条 UI | UI | ✅ 非目标 |
| 8 | 生命值 UI | UI | ✅ 非目标 |
| 12 | **移动对象（玩家块）** | 目标槽标记 | ❌→✅ **发动作会动** |

**结论：ls20 的感知必须新写，不能改 perceive.py 硬套。且「移动对象=色12」只能靠线上发动作实测，单帧判断会错。**

## 4. move 的 init 字段清单（已定稿）

映射到 `WorldState`（`longquan/interactive/state.py`）：

| WorldState 字段 | 从帧提取 | 提取规则 | 状态 |
|-----------------|---------|---------|------|
| `grid_w / grid_h` | 帧尺寸 | 64×64（或地板区 40×25） | ✅ 已定 |
| `cursor` | 移动对象位置 | 色12 bbox 锚点（5px 步进） | ✅ 已定：色12 左上角 |
| `walkable` | 地板 | 色3 集合 | ✅ 已定 |
| `goals` | 目标标记 | 色0/1 的 3×3（move 目标） | ✅ 已定 |
| `steps_limit` | 步数上限 | 42（源码逆向 StepCounter，见 verify-games.md） | ✅ 已定 |

**「已定」的能直接写**：cursor=色12、walkable=色3、goal=色0/1、步长=5px、方向映射=ACTION1/2/3/4=上下左右。init 现在是纯体力活（色块定位 + walkable 提取），可派给公司团队。

## 5. 移动步长 / 坐标系统 / 移动对象（线上实测结论）

三个未知一次性解决：

1. **坐标系统**：64×64 单层像素帧。
2. **移动步长**：5px 离散步进（不是 1px，也不是 3px sprite 对齐）。
3. **移动对象**：色12（5×2 块）。方向映射：ACTION1=上(y-5)、ACTION2=下(y+5)、ACTION3=左(x-5)、ACTION4=右(x+5)。

**撞墙语义**（对齐 move.step 设计）：移动对象 bbox 不变、返回 200 正常响应、state 不变——即「撞墙仍耗一步」，与 move.py 的 `step` 实现一致。

**探路协议要点**（复现用）：`/api/scorecard/open` 会 set-cookie `GAMESESSION`，后续 `/api/cmd/RESET` 和 `/api/cmd/ACTION{n}` 必须带同一 Session 的 cookie，否则 RESET 报 400 "game not found"。纯 requests 用单 `requests.Session()` 贯穿即可。
