---

## 0. 要解决什么

方法论说：**规则原语量小可穷尽，组合量大易爆；会学 = 在可穷尽的原语层上，用组合语法覆盖会爆的组合层。**

这份设计回答两个具体问题：

1. **一个原语「长什么样」**——它暴露哪几个函数，才能既被搜索调用、又被选择器挑选？
2. **原语选择器怎么工作**——面对新游戏，程序怎么在几个原语里选出对的？

---

## 1. 一个原语是什么

一个原语 = **一个「规则族」**。它不是某个游戏的规则，是「一类规则的算法骨架」。

| 原语 | 规则族 | 自由参数（可搜） |
|------|--------|-----------------|
| reflect 反射 | 对象关于某条线对称 | 线的位置、方向（横/竖） |
| translate 平移 | 对象整体位移 | 位移向量 (dx, dy) |
| recolor 颜色映射 | 颜色按映射表变换 | 映射表 |
| copy 复制 | 对象复制若干份 | 份数、偏移 |

注意：**参数是原语的一部分，但「参数枚举」不在原语内部**——它由 search 统一负责（见 §3）。原语只回答「给定参数，覆盖怎么算」。

---

## 2. 原语的统一接口（三个函数）

> **注意（2026-09-05 更正）：本「三函数」只统一了「几何族」（reflect/translate/recolor/copy 等网格变换原语）。** 交互族（move/mate/match/sequence/gravity/waypoint）走另一套「状态机」接口（`init/actions/step/done`），见 `docs/primitive-interface-interactive.md`。因为交互规则的「消除/盖印/时序/步数上限」塞不进「配置→覆盖」的纯函数契约。

每个原语模块暴露三个函数，签名统一：

```python
# 1. 匹配度：这个原语跟当前观测像不像？0~1 的先验分数
def score(obs: Obs) -> float

# 2. 覆盖：给定参数 + 对象位置，算出覆盖哪些格（返回 set）
def cover(obs, param, obj_cells, pos) -> set

# 3. 反推：给定参数 + 目标，反推对象该在哪些位置（返回候选位置列表）
def backproject(obs, param, obj_cells, targets) -> list[pos]
```

**为什么是这三个，不是别的？**

- `score` → 给选择器用：新游戏来了，先看哪个原语的「先验匹配」高，优先试那个。这解决「面对 25 款游戏，从哪个原语开始猜」。
- `cover` → 给 search 用：搜索要「验证某个位置能不能覆盖目标」，需要原语算出覆盖。
- `backproject` → 给 search 加速：反推「哪些位置才可能覆盖目标」，避免全棋盘暴力搜。

**关键设计：`param` 是自由的、由调用方传入。** reflect 的 param 是「线位置」，translate 的 param 是「位移向量」。原语自己决定 param 长什么样，search 不关心——search 只负责「枚举候选 param + 调用 cover」。

这就是「可搜」的来源：参数空间对 search 是统一的「候选集合」，原语是「怎么用参数算覆盖」。

## 3. 原语选择器的工作流（L2 的入口）

面对新游戏（没读过源码）：

```
1. perceive → Obs（通用结构，不含游戏知识）
2. 对原语库每个原语算 score(obs)，按分数排序
3. 逐个原语：
   a. 枚举该原语的候选参数（如 reflect 枚举所有可能的线位置）
   b. 对每个参数：search 解对象位置 → motion 出动作 → 回放验证
   c. 回放通过 → 这个原语 + 这个参数 = 真规则，收工
   d. 回放全失败 → 换下一个原语
4. 原语库耗尽 → 报「无法归纳」，诚实降级
```

**这跟现在的 loop 有什么不同？** 现在 loop 是「固定用 mirror 一个原语」；加了选择器，loop 变成「遍历原语库」。

---

## 4. 组合的预留（第一版不做，但接口留好钩子）

组合 = 一个游戏的规则是多个原语的复合（如「先反射再变色」）。

**钩子已经在接口里**：`cover` 返回 `set`。两个原语组合 = 两个 cover 的**并集**（或复合）。因为 set 天然支持并集，组合不需要改接口，只需要未来加一层「组合器」。

> **这只适用于几何族之间的组合。** 交互族的组合 = `step` 的**序列**（先 move 后 match，状态逐步演化），不是 set 并集。交互族的「组合器」是状态空间搜索器，见 `docs/primitive-interface-interactive.md` §5。

**第一版边界（明确不做）**：只支持单原语。先证明「单原语能从 AR25 迁移到 ft09」，再谈组合。否则一口吃不成胖子。

## 6. 一个诚实的边界

这套接口**第一版只解决「单原语的识别 + 参数搜索」**，它把 M1 的 L1「已知规则搜参数」升级成「**已知原语库，搜是哪个原语 + 什么参数**」。

这还不是完全的 L2「未知规则归纳」——因为原语库本身还是「人预定义的」。但它往 L2 迈了关键一步：**程序不再被绑死在单个游戏规则上，而是在一个规则族之间做选择。**

完全的 L2（连原语都自己归纳）是更远的目标，不在第一版。
